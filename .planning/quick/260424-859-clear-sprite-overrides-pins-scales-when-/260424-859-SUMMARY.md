# 260424-859: Clear sprite overrides on grouping change summary

Enforced the grouping contract: toggling any grouping axis via the Moshpit
settings panel now wipes all sprite pins and scale overrides so clusters
reflow cleanly. Sort-mode and grid-spacing changes still preserve overrides.

## What was added

1. **src/views/MoshpitView.vue**
   - Imported `watch` from vue, plus `useMoshpitFilterStore` and
     `useMoshpitOverrideStore`.
   - Instantiated `filterStore` and `overrideStore` alongside the existing
     store handles.
   - Added a single shallow `watch(() => filterStore.activeGroupings, ...)`
     that calls `overrideStore.clearAll()` on every array-identity change.
   - Doc comment explains why the watch lives here and why sort/spacing are
     not triggers.

2. **src/views/MoshpitView.test.ts** — three new tests in a dedicated
   `MoshpitView override-clear on grouping change` describe block:
   - **Positive:** seeding a pin and a scale, then calling
     `filterStore.toggleGrouping('workflow')`, drops `records.size` to 0 and
     flips `isPinned('abc')` to false.
   - **Negative (sort):** `setWithinClusterSort('oldestFirst')` leaves
     `records.size === 2`.
   - **Negative (spacing):** `setGridSpacing(600)` leaves
     `records.size === 2`.

## Why the watch lives in MoshpitView.vue

- **Layering.** `moshpitFilterStore` must not import `moshpitOverrideStore`
  (and vice versa) — they are peer platform stores with independent public
  APIs. The view is the one place that naturally owns both.
- **AGENTS.md #25.** We considered `computed` but the behaviour is side-
  effectful (triggering a store action + IDB clear), so `watch` is the
  correct primitive.
- **Renderer purity.** `useMoshpitSpriteLayer` / `resolveSlot` stay untouched
  — the cross-store coupling does not belong in the pure render path.

## Why shallow watch is sufficient

`toggleGrouping` always reassigns `activeGroupings.value` to a brand-new
array (spread or filter — see `moshpitFilterStore.ts:138-142`). Reference
identity changes on every toggle, so a shallow watch fires reliably. Deep
watch would be strictly more expensive with no behavioural benefit.

## Surprises during setup

- **Pre-existing uncommitted state.** The main worktree had a mid-flight
  lightbox refactor (new `moshpitLightboxStore`, `MoshpitLightboxOverlay`,
  `MoshpitAssetMetadataPanel`, `useMoshpitLightboxKeybindings`, matching
  `MoshpitView.vue` + `MoshpitView.test.ts` edits). That work was carried
  into this worktree as a baseline `chore:` commit so the override-clear
  commits stay atomic and don't co-mingle with unrelated refactor changes.
- **Pre-commit hook noise.** `pnpm typecheck` emitted TS2688 errors for
  `src/workbench/extensions/manager/**/*.vue` about unresolved Vue
  `language-core` `.d.ts` paths (relative paths generated by Volar point
  outside the worktree). The errors are unrelated to any file touched by
  this plan; the husky pre-commit still permitted the commit to land.
  SCOPE BOUNDARY applies — not fixed here.
- **testing-pinia behaviour.** `createTestingPinia({ stubActions: false })`
  lets the real `toggleGrouping` / `clearAll` actions run, and the async
  `clearAllOverrides()` IDB call inside `clearAll` rejects in happy-dom
  but is swallowed by the store's own `.catch(logPersistError)`. Tests
  stay clean.
